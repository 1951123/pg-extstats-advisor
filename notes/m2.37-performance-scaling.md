# M2.37 — Performance Scaling & Break-Even Evaluation

## 1. Research question

M2.37 measures the cost structure of the fixed-workload hypothetical
extended-statistics substrate.  It asks (A) when a one-time repository setup
amortizes as the number of evaluated configurations grows, (B) how native
repository acquisition changes with candidate count, and (C) whether changing
the acquisition input size changes the repeated physical-materialization
component while backend-local activation remains approximately stable.

The intended result is a measured cost decomposition, not a generic speedup
claim.

## 2. Why M2.36 was insufficient

M2.36 used six DMV designs and three repetitions as a bounded materialization
pilot.  It characterized one small suite but did not provide a configuration
count curve, a 256-configuration deterministic pool, candidate-count
repository scaling, or acquisition-input-size scaling.  M2.37 keeps the
M2.36 physical/hypothetical semantics and expands only the measurement scope.

## 3. Cost model

For a fixed sequence of designs, the measured decomposition is:

\[
T_{\mathrm{phys}}(D)=\sum_i(T_{create}+T_{analyze}+T_{explain}+T_{cleanup}),
\]

\[
T_{\mathrm{hyp,e2e}}(D)=T_{repo}(C)+\sum_i(T_{activate}+T_{explain}).
\]

The repository acquisition term is measured separately in Suite B.  The
removable materialization fraction is reported as the physical
materialization component divided by the physical per-design total.  The
reported break-even is the first measured prefix where the median
end-to-end-hypothetical curve is no greater than the median physical curve.
No universal or extrapolated break-even is claimed.

## 5. Experiment A protocol

The DMV frozen 30,000-row acquisition realization and the existing 72
candidate catalog were reused.  A deterministic seed (`2037`) generated 256
unique valid configurations containing empty/small, MCV-only, FD-only, mixed,
prefix, and pseudo-random subsets.  The same ordered candidates, workload,
ordinary-statistics state, target, and 1,963 planner calls were used in both
paths.

The physical path created the selected statistics objects, set target 100,
ran one relation-grouped `ANALYZE`, explained the workload, and cleaned up.
The hypothetical path registered the repository once, activated each ordered
subset, explained the same workload, and did not reacquire payloads per
design.  D-prefix cumulative medians were computed from per-design rows.

The measured first crossover is **D*=8**.  The C=72 repository acquisition

hypothetical component is 78.182 s.  The shared EXPLAIN component is dominant
in both paths, while cumulative physical materialization reaches 45.975 s at
D=256.

## 7. Break-even result

The first measured crossover is D=8, not a theoretical threshold.  The curve
is below one for D≤4 and above one from D=8 onward in this measured DMV
environment.  The result supports amortization of one-time acquisition/setup
over a fixed sequence of sufficiently many designs, but it does not establish
a universal D* or a production wall-clock guarantee.

## 8. Experiment B protocol

The frozen Census catalog was taken in stable precedence order and measured at
`C = 8,16,32,72,226,512,1024,2253,4506`.  Each point used one warmup and five
measured calls to the existing `acquire_payloads` API on PostgreSQL 16.14,
with a fresh temporary repository and cleanup after every run.  Repository
integrity, candidate count, payload digest loading, and final zero-statistics
cleanup were checked.

The current acquisition API exposes one aggregate call.  To avoid changing
product behavior, create-statistics, native `ANALYZE`, serialization, and
cache-write internals were not separately instrumented; the persisted raw
artifact labels this limitation explicitly.

## 10. Experiment C protocol

The isolated DMV database temporarily renamed the original relation, created
an unlogged `public.dmv` containing deterministic `ORDER BY ctid LIMIT N`
prefixes with `N = 30,000,60,000,120,000,240,000`, and restored the original
relation in a `finally` cleanup path.  For each N, the 72-candidate native
repository was acquired once and the six-design M2.36 suite (empty, prefixes
1/5/16/30, final-31) was timed with one warmup and five measured repetitions.
The objective values are diagnostic only because the input population varies;
the cost timings are the purpose of this suite.

## 12. Correctness and fairness gates

* **Experiment A correctness: PASS.** All 1,280 physical/hypothetical
  measured configuration pairs had identical estimate-vector digest and
  objective; all physical payload checks matched; planner calls were 1,963 on
  both paths.
* **Experiment B repository integrity: PASS.** Every measured repository had
  the requested candidate count, valid payload manifest/digests, and no
  `UNREGISTERED` state; cleanup left no acquisition statistics.
* **Experiment C correctness interpretation:** not applicable to cross-N
  objective equality because N intentionally changes.  The fixed-design path
  used the same SQL workload and planner-call count for each N.
* **Fairness: PASS.** PostgreSQL version, target, workload, candidate order,
  fixed configuration sequences, and no-query-execution `EXPLAIN` protocol
  were held constant within each comparison.
* **Cleanup: PASS.** The DMV relation was restored to 11,591,877 rows and no
  `pgextadv_*` extended-statistics objects remained.

## 13. Interpretation

Overall signal: **MODERATE**.

Suite A gives a clear measured crossover at D=8 and shows physical cumulative
materialization diverging from the repository path as D increases.  Suite B
shows tractable acquisition through 4,506 Census candidates with repository
bytes increasing substantially.  Suite C confirms approximately flat
activation but does not show a monotone input-size widening of the gap, so the
stronger “input cost necessarily increases the advantage” interpretation is
not supported.

## 14. Threats to validity

This is one WSL2 machine, one PostgreSQL 16.14 build, one DMV realization for
Suite A, one deterministic row-prefix construction for Suite C, and no OS
cache flushing.  The physical path and hypothetical path share native planner
work but are not a general application-latency benchmark.  Suite B uses an
existing Census acquisition relation and reports the aggregate acquisition API
because internal phase instrumentation would change product code.  The
results therefore characterize this environment and protocol only.

## 15. Paper implications

No manuscript was modified.  If integrated later, the safe evidence-led claim
would be:

> Physical evaluation repeatedly pays statistics materialization as fixed
> configurations accumulate, whereas the hypothetical substrate pays
> candidate-state acquisition once and then changes optimizer-visible state
> through backend-local activation; in this measured DMV environment, the
> curves crossed at D=8.

The results do **not** support generic speedup, production savings, arbitrary
candidate-space scalability, monotone input-size benefit, or larger-sample
correctness claims.

## 16. Decision

Retain M2.37 as a bounded performance-cost characterization.  It strengthens
the avoided-materialization evidence beyond M2.36, while the moderate signal
and Suite C non-monotonicity argue against adding a broad performance claim to
the frozen manuscript without a separate review.
