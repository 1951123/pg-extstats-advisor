# M2.36 — Bounded DMV Physical-Per-Design Materialization Pilot

## Scope

This is a diagnostic DMV-only timing pilot.  It quantifies measured physical
materialization work for a small deterministic design suite; it does not claim
universal speedup, end-to-end advisor acceleration, production benefit,
advisor superiority, query-latency improvement, or Census-scale physical
replay.  The paper was not modified.

The authoritative frozen implementation remains `paper-v1-system` at
`88797e4b82ff1d5c8bbba28dc27987af78ce78ad`.  The experiment runner is
`tools/dmv_m2_36_physical_materialization_pilot.py` and the complete raw
artifact is under
`experiments/dmv-m2-36-physical-materialization-pilot/`.

## Protocol and provenance

The pilot reused the M2.18/M2.35 DMV frozen sample and native repository:

- PostgreSQL 16.14, patched advisor backend, database `pgextadv_exp16_dmv`;
- 1,963 effective DMV queries, fixed order, fixed truth and objective;
- statistics target 100;
- frozen sample semantic digest
  `59dc8dbe007a81cbd10a11894ff8abf9b4a8f0cac11523221dbd63e34dd4ca7f`;
- sample binary digest
  `c3b30ddfebf118cb9137bae122e2913e19e88d0cbee14b2c93e980c7693cf463`;
- payload repository
  `.build/artifact-cache/dmv-m2-17b-frozen-sample-v1/repository`;
- one untimed warmup and three measured repetitions per design/path;
- no OS or PostgreSQL cache flushing; results are environment-specific.

The recorded environment is WSL2 Linux on x86_64 with 24 CPUs, approximately
15.62 GiB reported memory, and approximately 763.8 GiB available filesystem
space at measurement time; PostgreSQL used `shared_buffers=128MB`, `work_mem=4MB`,
`jit=off`, and two parallel workers.

The six predeclared designs were: empty; accepted ADD trajectory prefixes
1, 5, 16, and 30; and the final 31-object recommendation (8 MCV, 23 FD).
All selected candidates were `PRESENT`; every design records its ordered
candidate digest in `design-suite.json`.

The physical path used one batched CREATE/ALTER-statistics sequence, one
relation-grouped `ANALYZE`, catalog/payload verification, the common native
`EXPLAIN` workload, objective computation, and cleanup.  The hypothetical path
used one-time shell creation and repository registration, then per-design
ordered backend-local activation, the same native `EXPLAIN` workload, and
objective computation.  Activation replaces the active list; the backend-wide
reset is used only at final teardown so one-time repository registration is not
repeated per design.

## Aggregate result

- Median physical materialization component: **0.116797 s** (range
  0.065887–0.218108 s).
- Median hypothetical activation component: **0.000421 s** (range
  0.000296–0.000542 s).
- Median physical total: **0.392098 s** (range 0.351250–0.494663 s).
- Median hypothetical total: **0.279452 s** (range 0.256321–0.304600 s).
- Median physical/hypothetical total ratio: **1.414x** (range 1.326–1.668).
- One-time setup: repository load 0.001779 s, frozen-sample reconstruction
  0.468585 s, shell setup 0.016400 s, repository registration 0.019170 s.
- Transparent median-delta break-even estimate: **0.321 design evaluations**,
  using one-time hypothetical setup divided by median
  (physical-materialization minus hypothetical-activation) cost.  This is a
  descriptive amortization calculation, not a deployment or speedup claim.

## Interpretation

The practical signal is **MODERATE** for this bounded DMV environment: the
physical path consistently costs more, but common EXPLAIN dominates the total,
so total ratios are only 1.326–1.668x.  The result supports the narrow claim
that repeated physical materialization is a measurable cost component that the
backend-local path avoids in this controlled sequence.  It does not support a
general speedup claim or any broader performance conclusion.

No search, sampling, maintenance calibration, PostgreSQL patch, production
database, or manuscript was changed.  Final database cleanup verified zero
pilot statistics/data rows and no frozen sample relation.
